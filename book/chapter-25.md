# Часть VII. Производительность

## Глава 25. Производительность современных приложений

В 2026 году производительность веб-приложений окончательно вышла за рамки банальной «скорости загрузки страниц». Архитектурный фокус сместился на комплексные стандарты **Core Web Vitals** и общее качество цифрового опыта, где определяющее значение приобрели метрики отзывчивости интерфейса и визуальной стабильности.

---

### Ключевые метрики Core Web Vitals

* **INP (Interaction to Next Paint):** в современной веб-разработке INP закрепился в статусе главного барометра интерактивности, фиксируя задержку между действием пользователя и визуальным обновлением кадра («хорошим» считается результат до 200 мс). Передовые фреймворки спроектированы специально для устранения ресурсоёмких циклов контроля изменений, минимизирующих эту задержку: Angular — через zoneless-режим (стабилен с версии 20.2, по умолчанию с версии 21), Vue — через Vapor Mode, который на момент написания книги находится в статусе release candidate в составе Vue 3.6 и должен стабилизироваться осенью 2026 года.
* **LCP (Largest Contentful Paint):** ключевой индикатор скорости отрисовки основного контентного блока. Индустрия осознала, что оптимизация LCP давно вышла за пределы банального сжатия графики; сегодня решающую роль играют быстродействие сервера (TTFB) и грамотная приоритизация сетевых ресурсов.
* **CLS (Cumulative Layout Shift):** метрика визуальной стабильности макета. Использование продвинутых сборщиков и строгих правил разметки (в первую очередь — явное резервирование места под изображения, рекламные блоки и веб-шрифты) позволяет удерживать значения сдвигов заметно ниже порогового значения 0.1, при котором CLS ещё считается «хорошим» по методологии Core Web Vitals.
* **TTFB (Time to First Byte):** время ожидания первого байта от бэкенда. Этот параметр сокращается за счёт массового перехода на вычисления на периферии (edge rendering) и внедрения потоковых протоколов.

### Interaction Latency и отзывчивость интерфейсов

Суммарная задержка взаимодействия (*interaction latency*) рассматривается инженерами как многоуровневая задача, объединяющая издержки на выполнение скриптов, парсинг разметки и рендеринг DOM. На этом фоне архитектурные подходы вроде **resumability** (реализована в Qwik) заметно меняют правила игры, позволяя интерфейсам быстро «подхватывать» управление без прохождения тяжёлой фазы гидратации — хотя, как обсуждалось в главе 20, эта экономия времени на клиенте не бесплатна и частично оплачивается дополнительным весом служебной разметки в HTML.

---

### Современные техники оптимизации

* **Streaming (потоковая передача):** механизмы вроде потокового HTML-рендеринга в React (Suspense) и Next.js позволяют серверу отдавать документ по частям по мере их готовности, не дожидаясь формирования финального ответа целиком.
* **Lazy Loading (ленивая загрузка):** помимо работы с компонентами, нативная поддержка атрибутов отложенной загрузки для медиаконтента и декларативные конструкции вроде блоков `@defer` в Angular позволяют подтягивать фрагменты интерфейса ровно в момент их приближения к области видимости пользователя (*viewport*).
* **Code Splitting (разделение кода):** сборщики нового поколения на Rust (Rspack, Rolldown, а также встроенный в Next.js Turbopack) обеспечивают автоматическое, гранулярное разделение приложений на микромодули. Пользователь загружает строго тот код, который необходим для отображения текущего экрана, разгружая сеть и процессор.

### Сравнительная эффективность архитектур

Аналитические отчёты HTTP Archive и Chrome UX Report из года в год демонстрируют заметный разрыв в производительности между разными подходами. Как уже отмечалось в главе 21, статические и контентно-ориентированные экосистемы — в первую очередь Astro, реальный процент прохождения Core Web Vitals у которого держится на уровне около 66% — стабильно опережают типичные показатели Next.js и Nuxt (по разным замерам чаще всего в диапазоне 25–35%, конкретные цифры зависят от методологии и датасета). Общая картина наглядно подтверждает: минимизация клиентского JavaScript остаётся одним из самых надёжных путей к построению по-настоящему быстрых веб-приложений — при том, что финальный результат в любом случае сильно зависит от хостинга и дисциплины команды в работе с изображениями и шрифтами, а не только от выбора фреймворка.
