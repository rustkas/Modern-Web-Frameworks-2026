# Часть IX. Будущее веб-разработки

## Глава 33. Browser Native UI

К 2026 году архитектура создания пользовательских интерфейсов совершила заметный виток в сторону приоритета нативных возможностей браузера. Современные Web API, поддерживаемые движками Blink, Gecko и WebKit, позволяют решать инженерные задачи, которые ещё недавно требовали подключения тяжеловесных сторонних библиотек. HTML и CSS всё увереннее выходят за рамки статуса примитивных средств разметки, превращаясь в высокопроизводительную, декларативную платформу для проектирования сложных UI-систем.

---

### HTML и CSS: надёжный фундамент экосистемы

HTML сохраняет роль базового семантического каркаса веба. В современную эпоху семантика важна не только для обеспечения универсальной доступности (accessibility), но и для эффективного взаимодействия с ИИ-агентами, которые опираются на стандартизированные деревья доступности (accessibility trees).

CSS выступает в качестве высокопроизводительного слоя визуализации. Благодаря инициативе Baseline инженеры могут увереннее внедрять передовые спецификации (включая вложенные селекторы, subgrid, контейнерные запросы и современные математические цветовые пространства), заметно снижая риск неожиданных расхождений в поведении между актуальными браузерами — с оговоркой, что «Newly available» и «Widely available» всё ещё означают разный уровень надёжности, как подробно разбиралось в главе 2.

---

### Popover и Dialog: управление «верхним слоем»

Работа с модальными окнами, всплывающими меню и оверлеями стала во многом декларативной и безопасной благодаря встроенным механизмам браузера:

* **Native Dialog:** тег `<dialog>` предоставляет стандартизированный способ реализации доступных модальных окон. Он автоматически управляет фокусом клавиатуры, экранирует фоновый контент и изолирует взаимодействие без необходимости реализации громоздких JavaScript-хуков или ручного управления слоями `z-index`.
* **Popover API:** инструмент для создания лёгких всплывающих элементов (подсказок, выпадающих списков, тостов), которые автоматически поднимаются в специальный `top layer` браузера, избавляя разработчика от написания логики закрытия по клику за пределами элемента или нажатию клавиши `Escape`.

---

### CSS Anchor Positioning: нативная привязка элементов

Одной из заметных возможностей интерфейсной разработки последних лет стало появление **CSS Anchor Positioning**. Модуль позволяет динамически позиционировать дочерние элементы относительно произвольных узлов-якорей декларативными средствами CSS:

* **Отказ от позиционирующих библиотек:** инженеры всё реже вынуждены подключать JS-менеджеры позиционирования (вроде Floating UI) для расчёта координат выпадающих списков при скролле или ресайзе окна.
* **Расчёт силами движка рендеринга:** браузер выполняет позиционирование на уровне собственного механизма компоновки страницы (а не как отдельный слой поверх готового макета), что при прочих равных даёт более плавный результат, чем пересчёт координат JavaScript-ом на каждый кадр. Как обсуждалось в главе 13, кросс-браузерная поддержка сложилась только в январе 2026 года (с релизом Firefox 147), поэтому на момент написания книги технология находится в статусе Baseline Newly available, а не Widely available, — и для проектов с широкой аудиторией на старых браузерах разумно предусматривать откат к тем же JS-библиотекам.

---

### View Transition API: эволюция навигации и MPA

**View Transition API** заметно меняет пользовательский опыт взаимодействия с веб-приложениями, но состоит из двух частей с разным уровнем зрелости:

* **Переходы внутри одного документа** (для SPA) достигли статуса Baseline Newly available в октябре 2025 года, когда поддержку добавил Firefox — то есть на момент написания книги эта часть API уже работает во всех трёх основных движках.
* **Междокументные переходы** (Cross-document View Transitions, для классических MPA) — более свежая и пока менее равномерно поддержанная часть спецификации: Chrome и Safari работают с ней стабильно, а вот статус поддержки в Firefox на момент написания книги описывается источниками противоречиво — часть отчётов фиксирует её появление в Firefox 147 (январь 2026 года), другие тесты середины 2026 года по-прежнему показывают анимацию только в Chromium и Safari. Прежде чем полагаться на междокументные переходы как на основной, а не резервный сценарий, стоит свериться с актуальными данными на caniuse.com — это тот случай, когда ситуация меняется быстрее печатного слова.
* **Фреймворк-интеграция:** современные инструменты (например, Astro) интегрируют этот API на уровне сборки, позволяя элементам интерфейса «перетекать» со страницы на страницу посредством минимальных декларативных описаний, автоматически откатываясь к обычной навигации там, где браузер API не поддерживает.

---

### Form API и эволюция сбора данных

Обработка пользовательского ввода вернулась к принципам веб-стандартов, получив более широкую платформенную поддержку:

* **Нативная потоковая передача:** браузеры поддерживают эффективную потоковую передачу (streaming) файлов и данных форм без создания избыточных буферов в памяти.
* **Синергия с Server Actions:** прямая привязка атрибута `action` в HTML-формах к серверным функциям обеспечивает быструю отправку данных и рабочий сценарий по принципу progressive enhancement даже при отключённом JavaScript — при условии, что форма действительно реализована через нативный `action`, а не только через клиентский обработчик, как отмечалось в главе 28.

Платформенный подход (platform-first) в 2026 году отражает эпоху, когда веб-фреймворки всё чаще выступают не как монопольные монолиты, а как тонкие адаптеры над встроенными возможностями браузера — хотя, как показывают Anchor Positioning и междокументные View Transitions, часть этих возможностей всё ещё находится в процессе выравнивания поддержки между движками, и разумная осторожность здесь так же важна, как и энтузиазм.
