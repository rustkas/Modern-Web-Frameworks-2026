# Часть VI. Современные фреймворки

## Глава 20. Qwik

К 2026 году фреймворк Qwik занимает принципиально уникальную, обособленную нишу в архитектурном ландшафте фронтенда. В то время как классические экосистемы потратили годы на глубокую перестройку своих концепций ради соответствия жёстким требованиям производительности (эволюционируя в сторону серверных компонентов и гранулярных сигналов), Qwik изначально проектировался вокруг единственной радикальной цели: обеспечение мгновенной загрузки (*instant-on*) для приложений любого уровня сложности. Проект остаётся действующим и развивающимся — на момент написания книги актуальная версия ядра находится в линейке 1.x (1.20 и выше), а команда постепенно превращает Qwik из продукта, курируемого компанией Builder.io, в проект, управляемый сообществом.

---

### Resumability: архитектурный ответ на издержки гидратации

Фундаментальный подход Qwik заключается в реализации концепции **resumability (возобновляемость)**. Традиционные фреймворки вынуждены выполнять дорогостоящую процедуру гидратации (*hydration*), заново исполняя килобайты JavaScript на клиенте только для того, чтобы «оживить» пришедшую с сервера разметку. Qwik исключает этот этап.

* Серверный рендеринг сериализует в итоговый HTML не просто статический текст, а информацию, достаточную для продолжения работы приложения без повторного исполнения кода: границы компонентов, расположение обработчиков событий и состояние.
* Браузер пользователя принимает готовый интерактивный документ без необходимости скачивать, парсить и выполнять тяжёлый скриптовый код на этапе старта.
* Это позволяет достичь очень низкого показателя времени до интерактивности (TTI — Time to Interactive) практически независимо от сложности приложения.

Стоит, однако, назвать вещи своими именами — команда самого Qwik открыто признаёт, что «возобновляемость даётся не бесплатно»: чтобы браузер мог продолжить работу приложения без повторного исполнения кода, эта информация о границах компонентов и расположении обработчиков должна куда-то попасть, а попадает она в разметку — в виде дополнительных комментариев-маркеров и служебных атрибутов в HTML. В версии 1.x эта служебная разметка была довольно многословной; заявленная цель Qwik 2.0 — радикально сжать её кодирование (например, свернуть развесистую последовательность комментариев в компактную строку вроде `!{HDB1}`, вынесенную в конец документа одним тегом `<script type="qwik/vnode">`), одновременно материализуя только те виртуальные узлы, которые реально нужны для обработки конкретного пользовательского действия. Иными словами, resumability не отменяет компромиссы — она переносит их из JavaScript-бандла в объём HTML-разметки, и именно борьба с этим побочным весом остаётся одним из главных направлений работы над фреймворком.

### QRL и атомарная доставка кода

Для реализации ленивой загрузки Qwik использует специализированный механизм **QRL (Qwik URL)**. Вместо привычного статического или динамического импорта функций внутри бандла, фреймворк конвертирует ссылки на обработчики в сериализуемые строковые URL.

* Рантайм точно знает, какой именно фрагмент кода отвечает за реакцию на конкретное действие пользователя, не загружая этот код в память заранее.
* QRL обеспечивает автоматическое разделение кода (*code splitting*) не на уровне файлов или страниц, а на уровне отдельных функций и обработчиков событий.

### Lazy Execution: интеллектуальный отложенный запуск

Благодаря принципу возобновляемости, Qwik доводит философию **lazy execution** (ленивое выполнение) до логического предела.

* **Минимум JavaScript по умолчанию:** при первоначальной загрузке страницы в клиентский браузер передаётся минимальный объём исполняемого JavaScript — помимо самой разметки, требуется лишь небольшой (менее 1 КБ) загрузчик `qwikloader`, который слушает события и по требованию подгружает нужный код.
* Код конкретного обработчика подгружается и исполняется ровно в тот момент, когда пользователь совершает целевое действие (например, кликает по кнопке).
* Для предотвращения сетевых задержек при первом взаимодействии задействуется упреждающий механизм *prefetching*, фоново подтягивающий вероятно нужные фрагменты кода в моменты простоя браузера.

### Optimizer: компиляторная магия на Rust

В основе работы фреймворка лежит **Optimizer** — компилятор, написанный на Rust, который берёт на себя рутину по трансформации исходного кода.

* Компилятор автоматически разбивает компоненты на изолированные фрагменты, вынося логику обработчиков событий и эффектов в независимые микромодули.
* Optimizer подготавливает структуру под генерацию QRL-ссылок без какого-либо участия разработчика, воплощая принципы compiler-first архитектур.

### Qwik City: полноценный full-stack мета-фреймворк

Для проектирования крупных распределённых приложений экосистема предлагает **Qwik City** — официальный инструментарий для маршрутизации и работы с данными.

* **Файловая маршрутизация:** привычная структура директорий, определяющая архитектуру эндпоинтов и страниц.
* **Server Actions и Loaders:** декларативные инструменты для получения данных и мутаций на стороне бэкенда без необходимости вручную проектировать промежуточные слои API.
* Интеграция с middleware-решениями для реализации систем аутентификации и динамической обработки запросов.

---

### Edge-ready: глобальное распределение без барьеров

Архитектура Qwik изначально создавалась под требования парадигмы edge computing (Cloudflare Workers, Deno Deploy, Vercel Edge).

* Малый вес рантайма и отсутствие гидратационных циклов позволяют приложениям быстро стартовать на периферийных узлах сети с низкими показателями задержки (TTFB).
* Сериализуемость состояния упрощает передачу контекста между географически распределёнными серверами, способствуя бесшовному пользовательскому опыту в разных точках мира.

Qwik в 2026 году — это не просто альтернативный инструмент построения интерфейсов, а последовательное, честное в своих компромиссах переосмысление философии доставки кода в веб-среде: раздутый JavaScript — не единственная возможная плата за интерактивность, но и «бесплатной» возобновляемость не бывает — цена просто переносится в другое место, и команда фреймворка открыто работает над тем, чтобы сделать эту цену как можно меньше.
