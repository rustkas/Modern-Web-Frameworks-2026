# Часть V. HTML-first Frameworks

## Глава 13. Когда HTML снова главный

К 2026 году фронтенд-индустрия успешно замкнула масштабный виток исторической спирали, вернувшись к фундаментальной философии *HTML-first*. В этой парадигме язык гипертекстовой разметки больше не воспринимается как пассивный продукт жизнедеятельности массивных клиентских скриптов — он вновь признан главным, самодостаточным программным API современного браузера. Передовые фреймворки (включая экосистемы Astro и Svelte 5) прекратили попытки построения собственных виртуальных эмуляторов платформы, сфокусировавшись на максимальном использовании нативных возможностей движков, которые прежде приходилось обходить с помощью сторонних громоздких библиотек.

---

### Native Dialog и Popover API: конец эпохи костылей

Проектирование интерактивных модальных интерфейсов, диалоговых окон и плавающих элементов долгое время оставалось источником технического долга, вынуждая разработчиков вручную контролировать стеки наложения (*z-index*), перехват фокуса и обработку кликов за пределами элемента (*click-outside*) средствами JavaScript.

* **Native Dialog:** тег `<dialog>` предоставляет разработчику стандартизированный контейнер с безупречной доступностью (*a11y*), нативной поддержкой модального режима, автоматическим захватом фокуса и аппаратным управлением слоями.
* **Popover API:** стандартный декларативный механизм управления всплывающими подсказками, выпадающими меню и нотификациями. Браузер самостоятельно выстраивает такие элементы поверх остального контента в специальном слое (*top layer*) и управляет их жизненным циклом, избавляя команды от необходимости подключать сторонние позиционирующие утилиты вроде Popper.js.

---

### View Transition API: нативная плавность без SPA-монолитов

Одним из главных технологических прорывов стало повсеместное внедрение **View Transition API**. Этот стандарт позволяет анимировать визуальные переходы между абсолютно разными страницами или состояниями интерфейса с помощью лаконичных декларативных правил CSS.

Инструменты вроде Astro интегрировали это API на глубоком уровне, обеспечивая эффект «перетекания» элементов (*shared element transitions*) даже в классических многостраничных приложениях (MPA). Это избавляет проекты от необходимости удерживать тяжёлое SPA-состояние в памяти ради одной лишь плавности переходов.

---

### CSS Anchor Positioning: умное позиционирование силами стилей

Модуль **CSS Anchor Positioning** радикально упростил задачу привязки элементов интерфейса друг к другу. Инженер может явно объявить элемент «выпадающим списком» и зафиксировать его связь с кнопкой-якорем прямо в таблице стилей.

Браузер самостоятельно рассчитывает экранные координаты, учитывая текущую прокрутку страницы и границы вьюпорта, динамически перестраивая положение блока при изменении размеров. Это полностью снимает с главного потока процессора задачу вычисления координат в рантайме.

Стоит отметить, что кросс-браузерная поддержка сложилась совсем недавно: Chrome и Edge получили модуль ещё в марте 2024 года (версия 125), Safari — в сентябре 2025-го (версия 26), а последним подключился Firefox — в январе 2026 года, с релизом версии 147. Только с этого момента технология фактически стала доступна во всех трёх основных движках и, по логике Baseline из главы 2, вошла в статус Newly available — но не Widely available: этого более консервативного статуса, гарантирующего поддержку без всяких оговорок, стоит ожидать не раньше 2028 года. На практике это означает, что для проектов с широкой аудиторией на старых версиях браузеров всё ещё разумно предусматривать откат к JavaScript-библиотекам вроде Floating UI либо использовать полифилл.

---

### Эволюция форм (Forms): нативная валидация и Server Actions

Обработка пользовательского ввода и мутация данных в веб-приложениях стали значительно прозрачнее за счёт синергии нативных спецификаций и серверных возможностей фреймворков.

* Современные сборки (включая SvelteKit) задействуют встроенные механизмы ограничения данных, нативную клиентскую валидацию и потоковую передачу файлов через стандартные атрибуты форм.
* Интеграция с **Server Actions** позволяет отправлять данные форм напрямую на сервер силами самого браузера, обходясь без написания бойлерплейт-кода ручных `fetch`-запросов и сохраняя полную работоспособность приложения при временном отсутствии JS (принцип *progressive enhancement*).

---

### Web Components: Custom Elements и Declarative Shadow DOM

Веб-компоненты закрепились в статусе надёжного фундамента для создания переносимых, изолированных UI-библиотек, не привязанных к конкретным фреймворкам.

* **Custom Elements:** позволяют расширять базовый набор HTML-тегов кастомными элементами с инкапсулированной логикой, работающими в любой среде.
* **Declarative Shadow DOM (DSD):** технология, устранившая главный исторический барьер веб-компонентов — неспособность работать со связкой SSR. Теперь сервер может отдавать полностью инкапсулированную структуру теневого DOM (Shadow DOM) в первоначальном HTML-пакете — через атрибут `shadowrootmode` на элементе `<template>` — а браузер отрисовывает её мгновенно, не дожидаясь загрузки ни единого байта скриптов.

---

### HTML как главное API браузера

Философия веб-разработки зафиксировала победу прагматизма: современная веб-платформа представляет собой непрерывно развивающуюся экосистему встроенных возможностей, доступных инженеру «из коробки». Фреймворки сбросили балласт монолитных рантаймов, превратившись в изящную и эффективную прослойку между кодом разработчика и аппаратными возможностями браузерных движков (Blink, Gecko, WebKit).

Архитектура *HTML-first* гарантирует, что пользователь получает готовый, визуально завершённый документ мгновенно, что напрямую транслируется в высокие показатели **Core Web Vitals** (LCP и INP). JavaScript больше не является хрупким «скелетом», на котором держится всё приложение — он стал мощными «мышцами», подключаемыми точечно именно там, где декларативных возможностей нативных HTML и CSS объективно недостаточно.
