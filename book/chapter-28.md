# Часть VIII. Full Stack

## Глава 28. Server Functions

К 2026 году грань между клиентским и серверным окружением в веб-разработке стала гораздо менее заметной. Инженерам всё реже требуется вручную проектировать громоздкие REST- или GraphQL-контракты для каждого элемента интерфейса. На смену им пришла концепция **Server Functions** (серверных функций) — парадигматический сдвиг, позволяющий писать бэкенд-логику в виде обычных асинхронных функций, вызываемых напрямую из клиентского кода.

---

### RPC (Remote Procedure Call) сквозь призму компилятора

В основе Server Functions лежит проверенная временем модель **RPC** (удалённый вызов процедур), переосмысленная на уровне современных компиляторов:

* **Сквозная типизация (end-to-end type safety):** ведущие full-stack фреймворки (Next.js, SvelteKit, Astro, SolidStart, TanStack Start) обеспечивают передачу типов через сетевой барьер практически без ручной синхронизации. Если сигнатура серверной функции меняется, система фиксирует нестыковку на стороне клиентского компонента ещё на этапе типизации, до запуска в браузере.
* **Автоматизация эндпоинтов:** инфраструктура сборки анализирует код, генерируя необходимые сетевые маршруты и сериализаторы в фоновом режиме, снимая с разработчика значительную часть рутинной маршрутизации API.

Стоит помнить, что реализации этого паттерна расходятся не только в названиях (Server Actions в React, form actions в SvelteKit, Actions в Astro, Server Actions в SolidStart, server functions в TanStack Start), но и в архитектурной философии: как обсуждалось в главе 9, у Next.js server functions работают в связке с React Server Components и server-first моделью, тогда как TanStack Start сознательно построен как client-first фреймворк, где server functions — самостоятельный механизм, а не часть RSC-архитектуры.

---

### Actions: безопасность и server-first подход

Инструменты управления мутациями (известные в экосистеме React как Server Actions) стали одним из отраслевых стандартов выполнения логики на стороне бэкенда:

* **Изоляция среды:** выполнение кода строго на сервере обеспечивает безопасный доступ к базам данных, защищённым ORM и конфиденциальным API-ключам без риска их утечки в клиентский бандл.
* **Zero Bundle Size:** тела серверных функций исключаются из клиентской сборки, что заметно снижает объёмы загружаемого JavaScript.

---

### Мутации данных и управление состоянием

Server Functions стали основным инструментом для работы с побочными эффектами и изменениями данных:

* **Интеграция с кэшем и ревалидация:** сразу после выполнения мутации (например, отправки заказа или редактирования профиля) фреймворк может автоматически инвалидировать затронутые кэш-теги, синхронизируя интерфейс в рамках одного сетевого цикла.
* **Снижение объёма boilerplate-кода:** заметно меньше ручного управления флагами загрузки и промежуточными store-состояниями, а валидация данных не всегда приходится дублировать отдельно на клиенте и на сервере.

---

### Нативные формы и синергия с HTML

Современные серверные функции раскрывают свой потенциал в плотной связке со стандартными HTML-формами, возвращая разработчиков к классическим веб-примитивам через атрибут `action`:

* **Автоматическая сериализация:** фреймворк берёт на себя сбор данных из элементов формы в стандартный объект `FormData`, передавая его в качестве аргумента типизированной серверной функции.
* **Серверная валидация:** проверка входных данных происходит на бэкенде, а структурированные отчёты об ошибках возвращаются в UI для отрисовки без написания отдельных клиентских валидаторов с нуля.

---

### Progressive Enhancement: возвращение надёжности

Широкое распространение Server Functions вернуло в фокус философию **progressive enhancement** (постепенное улучшение):

* **Отказоустойчивость:** если клиентский JavaScript заблокирован, ещё не загружен или отключён пользователем, приложение (при условии, что форма реализована через нативный `action`, а не только через клиентский обработчик) не теряет работоспособности — форма отправляется по стандартному протоколу браузера с обновлением страницы.
* **Быстрый UX после гидратации:** как только гидратация завершена, фреймворк перехватывает событие отправки, превращая обычный запрос в асинхронный вызов без перезагрузки интерфейса, используя ту же самую серверную логику.

Server Functions в 2026 году заметно приблизили веб к целостной среде, где инженеры могут концентрироваться в первую очередь на бизнес-логике, делегируя платформе значительную часть сложности сетевой оркестрации — хотя, как показывает пример TanStack Start, у индустрии по-прежнему нет единого мнения о том, должна ли эта оркестрация обязательно строиться вокруг серверных компонентов.
