# Часть III. Rendering

## Глава 9. Server Components

К 2026 году архитектурный ландшафт веба окончательно закрепил парадигмальный сдвиг: сервер вернул себе статус главного вычислительного центра, в то время как клиентский JavaScript низведён до роли точечного дополнения, а не фундаментального каркаса приложения. Центральным элементом этой трансформации стали **React Server Components (RSC)** и их концептуальные аналоги в других экосистемах, навсегда изменившие характер взаимодействия клиента и бэкенда.

---

### React Server Components (RSC): вычисления на стороне сервера

**React Server Components** — это принципиально новый класс компонентов, которые исполняются исключительно на сервере. В отличие от традиционных компонентов, их код никогда не попадает в итоговый JavaScript-бандл, отправляемый пользователю.

**Ключевое отличие от SSR.** Важно понимать разницу: SSR (Server-Side Rendering) превращает React-компоненты в HTML-строку на сервере и отправляет её клиенту. RSC не генерируют HTML — они генерируют специальный сериализованный поток данных (Flight-поток), который содержит описание дерева компонентов и их пропсов. Клиент получает не готовый HTML, а данные, на основе которых он строит DOM. SSR определяет, *как* превратить React-дерево в HTML для конкретного запроса. RSC определяет, *какое* дерево вообще отправляется на клиент и какие компоненты будут исполняться на сервере, а какие — на клиенте.

**Асинхронные компоненты и прямой доступ к ресурсам.** RSC могут быть асинхронными функциями с использованием `async/await`. Это означает, что внутри компонента можно напрямую обращаться к базе данных, файловой системе или внутренним микросервисам без создания промежуточных API-эндпоинтов:

```tsx
import { db } from "@/lib/db";

export default async function BlogPost({ id }: { id: string }) {
  const post = await db.post.findUnique({ where: { id } });
  // Пост загружен напрямую из БД
  return (
    <article>
      <h1>{post.title}</h1>
      <div>{post.content}</div>
    </article>
  );
}
```

Такой подход полностью избавляет разработчика от необходимости писать отдельные API-роуты для каждого запроса данных, что сокращает количество кода и упрощает архитектуру.

**Zero Bundle Size (нулевой вес для клиента).** Тяжёлые зависимости — библиотеки для работы с базами данных, парсеры Markdown, утилиты форматирования дат, ORM-библиотеки — остаются на сервере. Например, если компонент использует библиотеку `marked` (50 КБ) и `sanitize-html` (25 КБ) для рендеринга Markdown-контента, эти 75 КБ кода никогда не отправляются в браузер. Это радикально сокращает объём загружаемого JavaScript, экономя ресурсы мобильных устройств и улучшая метрику INP.

**Безопасность.** Вся чувствительная бизнес-логика, доступы к API, секретные ключи и прямые SQL-запросы скрыты в контуре сервера. RSC никогда не попадают в клиентский бандл, поэтому риск утечки критической информации исключён.

**Ограничения.** Server Components не могут использовать хуки состояния (`useState`), эффекты (`useEffect`), обработчики событий или браузерные API (`window`, `document`). Это не произвольные ограничения — они гарантируют, что компонент никогда не потребует клиентского JavaScript. Когда требуется интерактивность, компонент помечается директивой `"use client"` и становится Client Component.

### Server Functions и Server Actions: стирание границ

С появлением **Server Actions** грань между фронтендом и бэкендом стала практически неразличимой. Инженеры получили возможность писать серверный код в виде инкапсулированных функций, которые вызываются напрямую из клиентских обработчиков событий.

**Механизм работы.** Функция, помеченная директивой `"use server"`, становится Server Action. Когда клиент вызывает эту функцию, React сериализует аргументы, отправляет сетевой запрос на сервер, выполняет функцию там и возвращает результат обратно клиенту.

```tsx
// actions.ts — серверный код
"use server";
import { db } from "@/lib/db";
import { revalidatePath } from "next/cache";

export async function addComment(postId: string, content: string) {
  await db.comment.create({ data: { postId, content } });
  revalidatePath(`/posts/${postId}`); // Автоматическая инвалидация кэша
}

// Client Component
"use client";
import { addComment } from "./actions";

export function CommentForm({ postId }: { postId: string }) {
  return (
    <form action={addComment.bind(null, postId)}>
      <input name="content" />
      <button type="submit">Отправить</button>
    </form>
  );
}
```

**Прогрессивное улучшение.** Когда Server Action передаётся в атрибут `action` формы напрямую из Server Component, форма становится прогрессивно улучшаемой: она может отправлять данные даже при полностью отключённом JavaScript или до загрузки клиентского бандла. Это возвращает веб-формы к их нативной природе, но с полной типобезопасностью и реактивностью.

**Автоматическая ревалидация.** После выполнения Server Action фреймворк может самостоятельно инвалидировать кэш и обновить затронутые компоненты. В Next.js это делается через `revalidatePath` или `revalidateTag`, в других фреймворках — через аналогичные механизмы.

**Server Functions без форм.** Server Actions не ограничены формами. Их можно вызывать из любых клиентских обработчиков — кликов, таймеров, эффектов — как обычные асинхронные функции, с полной поддержкой TypeScript-типов.

**Важное предостережение.** Server Actions — это публичные POST-эндпоинты, доступные из сети. Они требуют тщательной авторизации, rate-limiting и защиты от CSRF-атак. Это не приватные функции — это RPC-эндпоинты с типобезопасными точками вызова.

**Распространение паттерна Server Functions.** К 2026 году паттерн server functions перестал быть эксклюзивом Next.js — хотя стоит различать сам паттерн (типобезопасный RPC-вызов серверного кода из клиента) и полноценные React Server Components, которые сервер функции не предполагают. React 19 стабилизировал server functions через директиву `"use server"`. Astro выпустил стабильную версию Actions. **SolidStart**, дошедший к 2026 году до стадии релиз-кандидата версии 2.0 (текущая стабильная линейка — 1.x), поддерживает Server Actions и общую директиву `"use server"`. **TanStack Start** к середине 2026 года вышел из беты и достиг стабильного релиза 1.x — но важно понимать его философию: это не RSC-фреймворк, а сознательная альтернатива серверно-ориентированной модели React. Server functions здесь — не заменитель RSC, а самостоятельный, «клиент-первый» механизм RPC-вызовов, который автор фреймворка Таннер Линсли прямо противопоставляет подходу Next.js.

### HTML Streaming и Flight Protocol

Современный серверный рендеринг больше не требует от пользователя изнуряющего ожидания генерации всей страницы целиком. Streaming SSR и Flight Protocol вместе обеспечивают доставку контента по мере его готовности.

**Suspense и Streaming.** Глубокая интеграция с механизмами `Suspense` позволяет серверу отправлять клиенту лёгкий визуальный «скелет» (shell) моментально, а затем асинхронно достримивать тяжёлые блоки по мере их готовности:

```tsx
import { Suspense } from "react";

export default async function Page() {
  const hero = await getHero(); // Данные для хедера доступны сразу
  return (
    <main>
      <Hero data={hero} /> {/* Shell — отправляется мгновенно */}
      <Suspense fallback={<RecommendationsSkeleton />}>
        <Recommendations /> {/* Streaming — отправится позже */}
      </Suspense>
    </main>
  );
}

async function Recommendations() {
  const items = await getRecommendations(); // Медленный запрос
  return <RecommendationsList items={items} />;
}
```

**Механизм out-of-order streaming.** Suspense-границы могут разрешаться в любом порядке. React вставляет маркеры-плейсхолдеры в начальный HTML и использует небольшие inline-скрипты позже в потоке, чтобы заменить каждый плейсхолдер на реальный контент. Это позволяет быстрым источникам данных отрендериться раньше медленных, даже если они расположены позже в дереве JSX.

**Flight Protocol.** Уникальный внутренний протокол сериализации, используемый React для передачи структуры RSC в браузер. Flight-поток содержит три типа данных: отрендеренный вывод Server Components (разрешённое виртуальное дерево с элементами и пропсами), ссылки на Client Components (указатели на JavaScript-чанки и пропсы для их гидратации) и сериализованные пропсы для Client Components, поддерживающие расширенный набор типов по сравнению с `JSON.stringify` (промисы, итерируемые объекты, React-элементы).

Клиентский рантайм получает Flight-поток и использует его для построения DOM, загружая только те JavaScript-чанки, которые соответствуют Client Components в дереве.

### Server-First архитектура

Переход к полноценной **server-first архитектуре** ознаменовал окончательный отказ от устаревшей догмы, согласно которой всё приложение обязано целиком исполняться в браузере пользователя. Важно оговориться: как показывает пример TanStack Start выше, server-first — это доминирующая, но не единственная жизнеспособная философия 2026 года; часть индустрии сознательно выбирает альтернативные, client-first модели с server functions вместо RSC.

**Изменение ментальной модели.** Вместо вопроса «Сколько мы можем сделать в браузере?» разработчики в 2026 году всё чаще задаются вопросом «Что никогда не должно попадать в браузер?». В RSC-ориентированных фреймворках компонент по умолчанию становится Server Component, а `"use client"` — исключением, а не правилом.

**Вычислительная мощность.** Основная тяжесть рендеринга и обработки данных перенесена на мощные облачные серверы или распределённые периферийные узлы edge, находящиеся в минимальной сетевой близости от конечного потребителя. Edge-вычисления в 2026 году — это не специальная оптимизация, а стандартное место для выполнения request-time логики.

**Инженерная простота.** Разработчики могут использовать нативные возможности серверных платформ (прямой SQL-синтаксис, доступ к файловой системе, Web Crypto API) прямо внутри описания интерфейса, без необходимости создавать отдельные API-слои и синхронизировать типы между клиентом и сервером.

**Композиция рендеринга.** В 2026 году архитектура приложения строится из комбинации подходов: статический контент — через SSG, динамические данные — через потоковый SSR с RSC, интерактивные элементы — через Client Components (гидратация) или Islands Architecture (astro-острова), request-time логика — через edge-вычисления.

**Пример современной архитектуры.** Страница продукта может стримить заголовок, цену и описание через Server Component, загружать кнопку корзины и живые рекомендации как клиентские острова, выполнять аутентификацию и гео-таргетинг на edge, а статичные отзывы отдавать из CDN-кэша.

### Сравнительная таблица подходов Server Components

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| **React Server Components (RSC)** | • Zero Bundle Size — тяжёлые зависимости остаются на сервере<br>• Прямой доступ к БД и API<br>• Повышенная безопасность<br>• Снижение нагрузки на клиент | • Нет `useState` и `useEffect`<br>• Требует новой архитектурной модели<br>• Возможны сложности при миграции |
| **Server Actions / server functions** | • Стирание границ между фронтендом и бэкендом<br>• Прогрессивное улучшение форм (для форм на базе RSC)<br>• Автоматическая ревалидация кэша<br>• Полная типобезопасность | • Являются публичными POST-эндпоинтами<br>• Требуют авторизации и защиты от CSRF<br>• Возможны риски при неправильной конфигурации |
| **Streaming SSR** | • Мгновенный shell страницы<br>• Асинхронная доставка тяжёлых блоков<br>• Out-of-order streaming ускоряет быстрые данные | • Сложность реализации<br>• Требует продуманного использования Suspense<br>• Возможны проблемы с SEO при неправильной настройке |
| **Flight Protocol** | • Эффективная сериализация дерева RSC<br>• Поддержка расширенных типов пропсов<br>• Минимизация лишнего JavaScript | • Специфичен для React<br>• Требует глубокого понимания протокола<br>• Ограниченная совместимость с другими экосистемами |
| **Server-First архитектура** | • Основная нагрузка на сервер и edge<br>• Простота — меньше API-слоёв<br>• Гибкая композиция рендеринга<br>• Высокая безопасность | • Требует инфраструктуры edge и облаков<br>• Сложнее отлаживать распределённые вычисления<br>• Не всегда подходит для офлайн-сценариев |

Эта таблица помогает быстро оценить компромиссы: от точечных решений вроде **Server Actions** до философского сдвига в сторону **server-first архитектуры**.

Практические рекомендации по выбору подхода для разных типов проектов:

| Тип проекта | Рекомендуемый подход | Обоснование |
| --- | --- | --- |
| Контентные сайты (блоги, новостные порталы) | **RSC + Streaming SSR** | Большая часть контента статична, поэтому выгодно использовать Server Components для минимизации бандла и Streaming SSR для быстрой доставки текста и изображений. |
| E-commerce (интернет-магазины) | **Server Actions + Server-First** | Формы заказов и корзина требуют интерактивности и безопасности. Server Actions обеспечивают типобезопасные транзакции, а server-first архитектура позволяет вынести тяжёлую логику на сервер и edge. |
| Сложные SPA (CRM, дашборды) | **Flight Protocol + Selective Client Components**, либо **client-first server functions** (TanStack Start) | Сложные интерфейсы требуют гибкой сериализации и частичной интерактивности — либо RSC с точечными клиентскими компонентами, либо client-first фреймворк, где server functions подключаются по мере необходимости. |
| Медиа-платформы (видео, музыка) | **Streaming SSR + Edge Rendering** | Потоковый рендеринг позволяет быстро загружать shell и стримить тяжёлый контент, а edge-вычисления обеспечивают низкую задержку для глобальной аудитории. |
| Корпоративные приложения | **Server-First + RSC** | Высокая безопасность и работа с внутренними данными требуют минимизации клиентского кода и переноса логики на сервер. |

Таким образом, выбор подхода зависит от баланса между **интерактивностью**, **безопасностью**, **скоростью доставки** и **масштабируемостью**.

---

Server Components в 2026 году — это гораздо больше, чем просто локальная техническая фича конкретной библиотеки. Это новая философия веб-инженерии, где инфраструктура берёт на себя всю рутину по доставке данных и оптимизации бандлов, позволяя разработчику концентрироваться на бизнес-логике, а пользователю — получать мгновенный и безопасный доступ к контенту. Серверные компоненты, стриминг и edge-вычисления делают сервер не просто источником данных, а полноценной средой исполнения, способной конкурировать по отзывчивости с нативными приложениями, при этом сохраняя все преимущества веб-платформы.
