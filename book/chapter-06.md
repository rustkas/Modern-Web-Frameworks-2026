# Часть II. Reactivity нового поколения

## Глава 6. Управление состоянием

К 2026 году классическое управление состоянием (state management) полностью освободилось от догмы поиска одной «универсальной» глобальной библиотеки на все случаи жизни. Архитектура современного фронтенда опирается на принципы дифференцированного подхода, где для каждого типа данных подбирается наиболее нативный и быстрый инструмент. Главным индустриальным сдвигом стал окончательный отход от монолитных глобальных сторов в пользу гранулярной реактивности на базе сигналов и глубокой интеграции с серверным слоем.

---

### Карта состояний в современном приложении

Проектирование архитектуры приложения в 2026 году начинается с чёткого разделения данных по их природе и зоне ответственности. Не существует единого хранилища для всех типов данных — каждый тип требует своего подхода.

**Local State (локальное состояние).** Это данные, инкапсулированные в рамках одного компонента или небольшой группы связанных компонентов: состояние открытого модального окна, видимость выпадающего списка, текущее значение поля ввода, состояние анимации. В современных фреймворках локальное состояние реализуется через лёгкие локальные сигналы (например, `signal()` в Angular, `$state` в Svelte 5, `useState` с компиляторными оптимизациями в React). Этот тип состояния не требует глобального доступа и должен быть максимально лёгковесным, обеспечивая мгновенный отклик интерфейса без лишних проверок и перерисовок дерева.

**Global State (глобальное состояние).** Это контекст, доступный всему приложению: профиль текущего пользователя, языковая локаль, глобальная тема оформления, настройки доступности. Здесь на смену тяжеловесным паттернам с единым стором и редьюсерами пришли децентрализованные атомарные решения, где глобальное состояние собирается из независимых микросторов или атомов (как в Jotai). Каждый модуль или фича владеет своей частью глобального контекста, что упрощает тестирование и поддержку.

**Server State (состояние сервера).** Это асинхронные данные из удалённых источников — список товаров, профиль пользователя, комментарии, результаты поиска. Благодаря повсеместному внедрению Server Components и Server Actions граница между клиентом и сервером стёрлась: данные можно запрашивать декларативно прямо в теле компонента, а механизмы кэширования и инвалидации прозрачно контролируются на уровне фреймворка. Библиотеки типа TanStack Query автоматически управляют кэшированием, фоновым обновлением и повторными запросами, освобождая разработчика от ручного управления этим слоем.

**URL State (состояние URL).** Использование адресной строки в качестве источника истины для параметров сортировки, фильтрации, пагинации и навигации. В начале 2026 года новый **Navigation API** достиг статуса Baseline Newly available во всех основных браузерах (Chrome, Edge, Firefox 147, Safari 26.2) и предлагает единую, событийно-ориентированную модель навигации взамен разрозненного и местами непредсказуемого History API — например, событие `popstate` в старом API не всегда срабатывало при программных вызовах `pushState`/`replaceState`. Стоит, однако, помнить, что статус этой возможности пока именно Newly available, а не Widely available (до этого рубежа, по оценке WebDX, остаётся ещё около двух лет), а в Safari 26.2 всё ещё отсутствует поддержка `precommitHandler` — части API, отвечающей за более тонкие сценарии перехвата навигации. Поэтому библиотеки маршрутизации (React Router, TanStack Router) пока рассматривают Navigation API как перспективный низкоуровневый фундамент, а не как основание, на которое уже можно безоговорочно положиться в продакшене. URL при этом остаётся полноценным хранилищем состояния, которое сохраняется при обновлении страницы и доступно для расшаривания ссылками.

**Cache State (состояние кэша).** Это метаданные валидности данных — информация о том, является ли ответ свежим, требует ли фонового обновления, или его необходимо полностью перезапросить. В современных стандартах `fetch` с интеграцией кэша Service Worker и инструментах вроде TanStack Query эти процессы оптимизированы на уровне платформы, предоставляя разработчику декларативные механизмы управления временем жизни кэша.

**Event State (состояние событий).** Это краткосрочные данные взаимодействия: текущие координаты курсора при операциях drag-and-drop, состояние перетаскивания, активный элемент при наведении, положение скролла внутри контейнера. Эти данные обрабатываются через стандартные DOM-события и не требуют сохранения в реактивном сторе — они существуют только в пределах одного события или короткого жизненного цикла.

### Signals против классических подходов

Повсеместное появление встроенных сигналов в ядре ведущих фреймворков кардинально изменило ландшафт библиотек управления состоянием, предложив альтернативу классическим решениям.

**Signals vs Redux.** Классический Redux требовал написания огромного объёма шаблонного кода — actions, reducers, selectors, константы типов — и жёстко опирался на концепцию неизменяемости (immutability), требуя создания новых объектов при каждом изменении. Это приводило к необходимости использовать сложные утилиты (Immer, Immutable.js) или писать глубокие копии вручную. Сигналы обеспечивают мутируемость данных «под капотом» с автоматическим отслеживанием зависимостей. Изменение сигнала происходит через простой сеттер, без необходимости диспатчить action и писать reducer. Система сама знает, какие компоненты зависят от этого сигнала, и обновляет только их. Это избавляет разработчика от рутинного написания оберток и оптимизаций, заметно снижая когнитивную нагрузку и объём шаблонного кода.

**Signals vs MobX.** Идеологически эти подходы близки: оба используют реактивность и автоматическое отслеживание зависимостей. Однако нативные сигналы интегрированы непосредственно в компиляторы и системы сборки фреймворков. Например, в Angular 22 (стабильный релиз июня 2026 года, где API сигналов и Signal Forms окончательно перешли из экспериментального статуса в стабильный) сигналы являются неотъемлемой частью экосистемы, что гарантирует их оптимизацию на уровне статического анализа, минимальный размер итогового бандла (так как не требуется подключать отдельную библиотеку MobX) и полную совместимость с механизмами обнаружения изменений. MobX остаётся жизнеспособным решением для проектов на чистом React без фреймворка, но в экосистемах с развитым компиляторным слоем нативные сигналы имеют преимущество в производительности и размере.

**Signals vs NgRx.** В корпоративном сегменте Angular сигналы стали полноценной заменой громоздким цепочкам NgRx для большинства типовых задач, особенно для локального и простого глобального состояния. NgRx со своей архитектурой на основе Redux-паттернов, эффектов и селекторов остаётся актуальным для очень сложных систем с множеством бизнес-процессов, требованием к аудиту действий (action logging) и сложной межмодульной координацией. Однако переход на zoneless-архитектуру на базе сигналов позволяет полностью отказаться от избыточных потоков RxJS там, где достаточно чистой синхронной реактивности, сокращая сложность и повышая производительность.

### Современный инструментарий: Zustand, Jotai и TanStack

В тех сценариях, когда возможностей встроенных сигналов фреймворка недостаточно для организации сложной межмодульной логики, разработчики обращаются к специализированным библиотекам нового поколения, которые эволюционировали, учитывая уроки Redux и MobX.

**Zustand.** Уверенно закрепился в статусе стандарта для React-экосистемы благодаря предельной лаконичности и минималистичному API. Zustand позволяет создавать стор через простую фабричную функцию, используя синтаксис, близкий к обычным объектам JavaScript. Отсутствие бойлерплейта (не нужны провайдеры, обёртки, контексты) и лёгкая интеграция с хуками делает Zustand идеальным выбором для приложений, где нужно быстрое, простое и масштабируемое глобальное состояние. Zustand не привязан жёстко к React и может использоваться в других фреймворках с минимальной адаптацией.

**Jotai.** Предлагает элегантный «атомарный» подход к состоянию, вдохновлённый концепцией атомов из Recoil. Каждый атом — это независимая единица состояния, которая может зависеть от других атомов через функции-производные. Jotai позволяет собирать сложные взаимосвязанные хранилища из независимых микро-атомов, что обеспечивает гранулярную реактивность без избыточности. Преимущество Jotai — атомы легко комбинируются, тестируются и переиспользуются, а также поддерживают асинхронные вычисления «из коробки».

**TanStack Store.** Универсальное фреймворк-агностичное решение от создателей TanStack Query. Оно позволяет инженерам описывать сложную бизнес-логику и управление состоянием единожды, а затем переиспользовать код в проектах на React, Vue, Svelte, Solid или Angular. TanStack Store предоставляет строгую типизацию, интеграцию с Reactivity API и возможность создавать сложные сторы с методами, селекторами и реактивными зависимостями. Это критично для мультифреймворковых экосистем крупных компаний, где один и тот же слой состояния должен работать на разных технологических стеках.

---

Управление состоянием в 2026 году — это поиск баланса между локальной простотой и глобальной эффективностью. Платформа и компилятор берут на себя всю рутину по отслеживанию графов зависимостей, освобождая разработчика от ручной оптимизации. Инженер выбирает правильный инструмент для каждого типа данных: локальные сигналы для UI-состояния, Server Components для серверных данных, специализированные библиотеки для сложной глобальной логики. Это оставляет пространство для проектирования чистых и надёжных потоков данных, где каждый тип состояния управляется наиболее подходящим способом, а не универсальным, но тяжеловесным решением.
