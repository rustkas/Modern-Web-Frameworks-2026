# Часть III. Rendering

## Глава 7. Современные модели рендеринга

К 2026 году выбор стратегии рендеринга окончательно перестал быть примитивным бинарным спором в стиле «клиент против сервера». Современный стек веб-фреймворков оперирует гибкими гибридными архитектурами, которые позволяют органично комбинировать различные подходы не только в рамках одного проекта, но даже на уровне отдельных компонентов одной страницы. Абсолютный приоритет индустрии — мгновенная доставка полезного контента при сохранении безупречной интерактивности и минимальном потреблении ресурсов на устройстве пользователя.

---

### CSR (Client-Side Rendering): нишевый инструмент для сложных систем

Классическая модель одностраничных приложений (SPA), при которой браузер получает минималистичный HTML-скелет и массивный JavaScript-бандл, самостоятельно строящий весь интерфейс на клиенте, прошла проверку временем. В модели CSR сервер отдаёт практически пустую HTML-страницу с тегом `<div id="root"></div>` и набором тегов `<script>`, загружающих JavaScript. Весь процесс рендеринга — построение DOM, применение стилей, обработка событий — происходит на клиенте после загрузки и исполнения бандла.

Несмотря на справедливую критику за медленную первую загрузку (пользователь видит белый экран до тех пор, пока JavaScript не загрузится и не выполнится) и высокие требования к процессору, CSR удерживает прочные позиции в трёх узких нишах.

**Сложные внутренние веб-интерфейсы.** Корпоративные дашборды, административные панели, CRM-системы и браузерные редакторы (например, Figma, Google Docs) выигрывают от богатой интерактивности и возможности работать офлайн. Время первой загрузки менее критично для внутренних пользователей, работающих в стабильных сетевых условиях.

**Приложения с интенсивными вычислениями.** Системы, требующие частых обновлений интерфейса — финансовые трекеры, игровые интерфейсы, системы мониторинга в реальном времени — где серверный рендеринг добавлял бы ненужную задержку.

**Системы без требований к SEO.** Если приложение находится за логином и не индексируется поисковыми системами, преимущества SSR для SEO становятся неактуальными, и CSR оказывается проще в архитектуре и деплое.

### SSR (Server-Side Rendering): ренессанс серверного веба

Серверный рендеринг переживает масштабный подъём, вернувшись после периода доминирования SPA. Современные фреймворки (Next.js, Nuxt, Angular, SvelteKit) используют SSR в качестве фундаментального стандарта для разработки полнофункциональных full-stack приложений.

В модели SSR сервер динамически генерирует готовый HTML-код под каждый входящий запрос пользователя. Фреймворк на сервере выполняет компоненты, извлекает данные из базы данных или API, строит React/Vue/Angular-дерево и превращает его в строку HTML, которая отправляется клиенту. Пользователь мгновенно получает готовую страницу с контентом, а затем происходит гидратация — подключение JavaScript для интерактивности.

Этот подход обеспечивает два критических преимущества. Во-первых, идеальная индексация поисковыми роботами, которые получают полноценный HTML с контентом, а не пустой скелет. Во-вторых, мгновенная отрисовка первого кадра (First Paint / FCP) — пользователь видит контент практически сразу, без ожидания загрузки и выполнения JavaScript. Кроме того, прямой доступ к базам данных и внутренним микросервисам прямо на этапе серверного рендеринга позволяет собирать сложные страницы «на лету», минуя лишние прослойки API-шлюзов и сетевые задержки, что ускоряет общее время ответа.

### SSG (Static Site Generation): эталон контентной скорости

Генерация статических сайтов на этапе предварительной сборки (build time) остаётся непревзойдённым стандартом для контентных ресурсов, документации и маркетинговых платформ. В отличие от SSR, где HTML генерируется на каждый запрос, SSG создаёт все страницы заранее, в момент сборки проекта.

Сборщик проходит по всем маршрутам, выполняет компоненты, извлекает данные (например, из файлов Markdown, CMS или API) и генерирует статические HTML-файлы. Эти файлы затем деплоятся на CDN и отдаются пользователям практически мгновенно, без какого-либо серверного вычисления в рантайме.

Проекты вроде Astro довели этот подход до совершенства через философию static-first, исключая любой лишний JavaScript по умолчанию. Статические страницы мгновенно отдаются пользователю с ближайших узлов глобальных CDN, обеспечивая абсолютный пик производительности. Единственное ограничение SSG — контент должен быть известен на этапе сборки, что делает этот подход неприменимым для персонализированных или часто обновляемых данных.

### ISR (Incremental Static Regeneration): баланс статики и динамики

Стратегия инкрементального обновления статики (Incremental Static Regeneration, ISR), изначально популяризированная Next.js, в 2026 году продолжает решать фундаментальную проблему SSG: необходимость пересобирать все страницы при изменении контента.

ISR работает следующим образом. На этапе сборки генерируются все статические страницы. В рантайме, когда пользователь запрашивает страницу, она сначала отдаётся из кэша. В фоновом режиме фреймворк проверяет, не устарел ли контент (по времени или по триггеру), и если да — запускает перегенерацию этой конкретной страницы на сервере. Новая версия страницы сохраняется в кэш и будет отдаваться следующим пользователям.

Это означает, что системы кэширования больше не требуют полной пересборки всего веб-ресурса при изменении одной страницы. Интеграция с вебхуками CMS и баз данных позволяет мгновенно ревалидировать и обновлять точечные статические блоки по мере необходимости, объединяя скорость отдачи статики с актуальностью данных полноценного SSR. ISR идеально подходит для интернет-магазинов, блогов и новостных сайтов, где тысячи страниц сменяются постепенно.

### Streaming SSR: потоковая доставка контента

Традиционный серверный рендеринг заставлял пользователя ждать, пока сервер полностью подготовит HTML всей страницы — все асинхронные запросы к базе данных, API и внешним сервисам должны были завершиться до отправки первого байта. **Streaming SSR** кардинально изменил этот процесс, позволяя передавать документ по сети асинхронными фрагментами (chunks) по мере готовности данных.

Сервер начинает отправлять HTML-поток сразу же, как только готова статическая структура страницы. Он отсылает «скелет» страницы, используя Suspense-границы или аналогичные механизмы для обозначения динамических областей. Для каждой такой области сервер отдельно выполняет асинхронную загрузку данных и, по готовности, отправляет HTML-фрагмент в поток в правильной позиции. Браузер получает фрагменты по мере их поступления и встраивает их в уже отображённую страницу.

Этот подход даёт два фундаментальных преимущества. Во-первых, радикальное улучшение метрики TTFB (Time to First Byte) — пользователь получает первый байт ответа практически мгновенно. Во-вторых, возможность начать чтение и взаимодействие с контентом задолго до того, как завершится отрисовка периферийных элементов (например, тяжёлых графиков или списка комментариев). Такие механизмы, как React Suspense и потоковый рендеринг в Svelte 5, делают Streaming SSR стандартным режимом для современных full-stack фреймворков.

### Edge Rendering: вычисления на краю сети

Архитектура вычислений на «краю» сети (edge computing) перенесла логику обработки запросов с удалённых дата-центров на периферийные узлы CDN, находящиеся в физической близости к пользователю. Это стало возможным благодаря новым рантаймам: Vercel Edge Runtime, Cloudflare Workers, Deno Deploy и аналогичным платформам, которые поддерживают Web API и лёгковесные JavaScript/TypeScript среды.

В модели Edge Rendering серверная логика выполняется не в едином регионе (например, us-east-1), а распределённо по сотням точек присутствия по всему миру. Когда пользователь из Европы запрашивает страницу, она обрабатывается на европейском edge-узле, а не в дата-центре в США. Это минимизирует сетевые задержки (latency) и позволяет генерировать персонализированный HTML с субсекундным откликом в любой точке планеты.

Edge Rendering особенно эффективен для приложений с глобальной аудиторией, где каждая миллисекунда задержки влияет на пользовательский опыт. Однако edge-рантаймы имеют ограничения — меньший объём памяти, ограниченное время выполнения, отсутствие полноценного Node.js API — поэтому они лучше всего подходят для лёгковесной логики: рендеринг статических страниц с персонализацией, A/B-тестирование, гео-таргетинг, обработка запросов перед проксированием к основному серверу.

### Partial Rendering и PPR (Partial Prerendering)

Одним из самых заметных проявлений архитектурной эволюции рендеринга в 2026 году стал подход **Partial Prerendering (PPR)**, который объединяет преимущества SSG, SSR и Streaming SSR в единую модель на уровне отдельных компонентов. Идея впервые была представлена как экспериментальная в Next.js 14–15, а стабильной стала в Next.js 16 (октябрь 2025 года) — уже не как отдельный флаг `experimental.ppr`, а как часть более широкой архитектуры **Cache Components**, включаемой единым флагом `cacheComponents: true` и директивой `use cache` для явного управления кэшированием.

PPR работает следующим образом. Страница декларативно разбивается на статическую оболочку (shell) и динамические «дыры» (области, требующие персонализации или актуальных данных). На этапе сборки фреймворк генерирует статический HTML для всех статических частей страницы. В рантайме, при запросе, статический каркас отдаётся пользователю мгновенно из кэша CDN (как при SSG). Параллельно сервер начинает рендеринг динамических областей, которые требуют актуальных данных, — каждая из них оборачивается в границу `<Suspense>`. Каждая динамическая область обрабатывается независимо — данные запрашиваются, HTML генерируется и отправляется через Streaming SSR. Браузер получает динамические фрагменты по мере готовности и встраивает их в статический каркас.

Этот подход даёт три ключевых преимущества. Во-первых, мгновенная доставка статического каркаса — пользователь видит структуру страницы и навигационные элементы практически сразу. Во-вторых, параллельный рендеринг динамических блоков — они не блокируют доставку друг друга. В-третьих, минимальный клиентский JavaScript — гидратация нужна только для динамических областей, статика остаётся без JS. Сегодня PPR — это готовая, стабильная возможность Next.js App Router (доступная только там — ни Pages Router, ни классические SPA этой моделью воспользоваться не могут), и другие фреймворки (Nuxt, SvelteKit) активно внедряют аналогичные концепции статической оболочки с динамическими вставками.

---

Современные модели рендеринга в 2026 году — это не компромисс между скоростью и гибкостью, а многослойная гибридная инфраструктура. Разработчик выбирает стратегию для каждого маршрута, каждой области страницы, каждого компонента. CSR — для интерактивных виджетов, SSR — для динамических страниц, SSG — для статического контента, ISR — для часто обновляемых данных, streaming — для длительных запросов, edge — для глобальной аудитории. Комбинация этих подходов, управляемая на уровне фреймворка, гарантирует, что каждый байт разметки доставляется до браузера наиболее быстрым и рациональным способом, обеспечивая превосходный пользовательский опыт при минимальной нагрузке на серверные ресурсы.
